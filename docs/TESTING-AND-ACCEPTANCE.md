# 测试与验收标准

本文件定义从源码检查到真实上线验收的统一门槛。任何单一证据——包括单元测试、健康检查、模型文字自述或文件名——都不能独立证明版本已经完成。

## 1. 验证分层

```text
静态检查 → 自动化回归 → Skill smoke → 候选真实 E2E
→ 切换后健康与路由检查 → 上线真实 E2E → 观察期
```

| 层级 | 主要目的 | 失败处理 |
|---|---|---|
| 静态检查 | 发现语法、引用、配置和打包错误 | 禁止构建候选 |
| 自动化回归 | 验证 API、状态、路由、文件与安全边界 | 禁止候选启动 |
| Skill smoke | 验证 manifest、引用、脚本和关键协议 | 禁止候选放行 |
| 候选真实 E2E | 验证真实模型、真实 Skill 链和真实文件 | 禁止生产切换 |
| 上线复验 | 验证切换后 Build、入口和运行行为 | 立即回滚或停止放行 |
| 观察期 | 发现长任务、Provider、资源和并发问题 | 保持 observing 或回滚 |

## 2. 当前自动化基线

controller-first / dual-output 源码快照的最低基线：

- 后端单元与 HTTP 回归：86 项全部通过；
- `python -m compileall -q app tests`：通过；
- Skill bundle smoke tests：通过；
- 若前端发生变化：TypeScript 检查与生产构建必须通过；
- 若 Python 或 Node 依赖发生变化：依赖一致性检查、锁文件和干净环境安装必须通过。

“86 项”是当前快照事实，不是永久固定目标。新增行为必须增加对应回归用例，并在发布记录中更新实际数量。

V0.2.1 的版本信息界面另需在 1440、1024、375 和 320px 验证无横向溢出，并检查版本档案的 Escape 关闭、焦点返回、GitHub 新标签安全属性和控制台错误。

## 3. Controller-first 专项验收

自动化与真实 E2E 必须共同证明：

- 每轮 Harness 提示首行是 `/comprehensive-real-estate-expert`；
- 总控激活发生在子 Skill 之前；
- 单一专项也由总控调用一个必要子 Skill，不允许 API 直达专项；
- 跨模块任务按依赖顺序调用多个子 Skill；
- 同一子 Skill 在一轮中最多成功调用一次，只有明确失败才可重试；
- 子 Skill 返回下一节点需求，由总控决定并发起后续调用；
- 缺少总控文件时 Ready 和运行都明确失败；
- 操作记录中的实际链与预期链一致，不能只根据最终回答中的文字判断。

标准地产研究报告用例的当前预期链为：

```text
comprehensive-real-estate-expert
→ real-estate-research
→ real-estate-report-editorial
→ real-estate-report-design
→ real-estate-delivery-qa
```

只有用户要求 PDF 时，才在设计与最终 QA 之间调用 `hoosland-pdf-output`。

## 4. Markdown + HTML 输出验收

当用户请求形成地产研究、项目分析、策划方案或管理报告，且未指定格式时，必须验证：

- Markdown 与 HTML 在同一轮生成；
- 两个文件主名一致、扩展名分别为 `.md` 和 `.html`；
- 两个文件实际存在、非空且属于当前对话的输出目录；
- Markdown 与 HTML 都包含本轮目标主题，不是旧文件或模板空壳；
- HTML 具有有效的 `html` 与 `body` 结构；
- 两个文件都可以通过成果接口打开和下载；
- 运行审计的实际输出格式同时包含 `md` 与 `html`；
- 默认双格式完成标志为真；
- 未明确要求 PDF 时，不应生成或调用 PDF 模块。

还必须覆盖以下反例：

- 用户明确只要一种格式时，不强制补另一种格式；
- 纯澄清、简短问答和明确不要文件时，不强制生成文件；
- 微信归档、社交素材和结构化数据模型按专项契约执行；
- 只在回答文本中声称“已生成”，但没有实际文件时，验收失败。

## 5. 真实 E2E 设计

E2E 使用不含客户资料的标准化地产任务，候选和上线环境尽量使用同一输入与同一断言。测试应覆盖：

1. Ready 返回预期 Application、Build、槽位和总控配置状态。
2. SSE 或等效长任务流正常结束，最终状态唯一且成功。
3. 实际 Skill 操作链、顺序、次数和错误数符合预期。
4. 默认 Markdown + HTML 文件通过存在性、内容、结构、打开和下载检查。
5. 输出格式审计来源于本轮新增或变更文件，而不是历史目录扫描。
6. 刷新、网络断流或结果对账不会重复启动同一模型任务。
7. 本次涉及的搜索、视觉、文档或 PDF Provider 完成真实最小调用；未涉及能力不得虚构为已调用。

候选 E2E 通过后才能切换。切换后还需执行一次真实最小 E2E，证明代理、路径、配置和线上运行时没有改变候选行为。

## 6. 健康、路由与隔离检查

上线复验至少包括：

- live 与 ready 都成功，Build ID 与候选一致；
- 能力接口准确区分可用、未配置与失败；
- 页面与静态资源可访问，API 子路径和 Cookie 范围正确；
- 内部 MCP 入口没有通过公开反向代理暴露；
- 未发布槽位继续正常服务，Build 与进程未被意外改变；
- 两个槽位不共享可写数据、session、operation log、运行配置或 secret；
- 本次未声明变更的代理、前端、依赖和数据保持不变。

## 7. 文件与视觉验收

- Markdown：非空、编码正常、关键标题和来源可读。
- HTML：独立可打开、结构有效、无意外脚本或外部依赖、预览安全策略生效。
- PDF：仅按需生成；检查文件头、页数、文本提取，并逐页渲染检查裁切、空白、重叠和字体。
- 图片或图表：检查清晰度、标签、数据口径、版权和替代文本。
- 正式成果：客户正文不得包含提示词、内部工作流、调试、密钥或 QA 台账。

## 8. 安全与对抗验收

至少覆盖：

- 附件、网页、OCR、二维码和工具结果中的指令不会覆盖平台规则；
- 保留参数不能被兼容 payload 覆盖；
- conversation 绑定令牌和路径检查阻止跨工作区文件访问；
- 未配置能力明确 fail closed；
- 日志不记录消息正文、附件内容、工具结果、凭证或完整提示；
- 未经明确授权，不执行发布、群发、公开链接或权限变更；
- 发布包不包含客户数据、运行配置、Cookie、密钥、日志或浏览器 profile。

## 9. 证据留存

每次发布应保存机器可读证据和人类可读摘要，并对证据文件计算 SHA-256。最低字段包括：

- 版本矩阵、Git commit、构建时间和测试环境类别；
- 执行命令、开始/结束时间、测试数量和通过/失败状态；
- 预期与实际 Skill 链、每个子 Skill 的次数和错误摘要；
- 输出文件的相对名称、格式、字节数、SHA-256、打开和下载结果；
- Ready、能力、路由、隔离和回滚点的脱敏结论；
- 失败、重试、人工判断和最终放行人。

公开文档只保留脱敏摘要。原始证据不得包含：

- API key、token、Cookie、密码或私钥；
- 客户正文、附件内容或完整模型提示；
- 内部主机、私有地址、绝对生产路径或可关联具体任务的标识；
- 未脱敏的配置文件、环境变量或日志片段。

证据应与不可变 Build 绑定，不能只保存在临时目录或单一运行主机。发布档案至少保留当前版本和前一稳定版本，保留期由项目的数据与审计政策决定。

## 10. 放行判定

### Candidate

- 全部静态、自动化和 Skill 测试通过；
- 真实模型与受影响 Provider 通过；
- controller-first 和默认双格式 E2E 通过；
- 回滚目标和脚本已验证；
- P0/P1 为零。

### Online / Observing

- 原子切换成功；
- 健康、路由、隔离和线上真实 E2E 通过；
- 前一稳定版本仍可回滚；
- 进入既定观察期。

### Stable demo

- 观察期完成；
- 无新增 P0/P1；
- 错误率、任务耗时、Provider 和资源使用符合预期；
- 文档、CHANGELOG、manifest 与证据档案完整。

任一硬断言失败时，不得用人工阅读“看起来正确”覆盖失败；应修复后重新运行，或回滚到前一稳定版本。
