# ADR-0002：双槽发布与数据隔离

- 状态：Accepted
- 日期：2026-08-25

## 背景

工作台需要在保留可用基线的同时迭代新版本。原地覆盖同一个应用目录、Skill 目录和数据目录会导致：

- 新旧代码无法并行验收。
- 回滚点被覆盖，故障恢复依赖临时修补。
- 两个版本可能同时写入同一会话、Harness session 或日志。
- 加密配置、管理员会话和内部能力令牌可能跨槽混用。

## 决策

采用两个逻辑槽位承载交替版本。每个槽位拥有独立的服务身份、监听入口和可写状态；候选版本使用不可变 release 和版本化 Skill 目录，验证后再切换目标槽位。

### 必须隔离的可写状态

两个槽位不得共享：

- conversation 数据和工作区；
- Harness sessions；
- operation logs；
- 加密 runtime config；
- 管理员 session secret；
- 内部 MCP token；
- Build ID 与版本化 Skill 绑定。

客户数据默认不在槽位间迁移。确需迁移时，必须作为独立的数据变更定义授权、范围、备份、校验和回滚。

### 不可变发布

- 每个构建进入新的只读 release 目录。
- 在线 release 不原地修改。
- 目标槽位停止服务后，分别以原子文件操作切换应用引用和环境配置。
- 至少保留前一个可用 release、匹配的 Skill 目录和环境配置备份。
- 应用与 Skill 的已验证组合是同一个一致性单元，必须一起切换和一起回滚；这不表示两个文件系统操作构成跨文件事务。

### 共享组件边界

只读基础组件可以在兼容性得到验证时共享；可写业务状态不能共享。若某次热修沿用共享 Python 环境，必须确认 requirements 未变化且不执行依赖安装。长期基线仍优先让构建依赖随 release 可复现。

反向代理或首页入口不是每次热修都必须修改。应用内部行为升级且公网路由未变化时，不应为了发布形式而 reload 代理。

## 发布流程

1. 生成应用、Skill、清单和校验值。
2. 在隔离候选环境完成静态测试、单元测试和真实 E2E。
3. 切换前确认目标槽位没有活动任务。
4. 停止目标槽位，复查进程、监听和活动状态。
5. 原子切换应用 release 与匹配的环境/Skill 绑定。
6. 启动并验证精确版本、槽位、前端和 Agent Ready。
7. 完成内部入口和公开入口的受控验收。
8. 保留候选证据与旧回滚点。

任何硬探针失败都应恢复旧应用与旧环境绑定，并验证旧版本重新 Ready。

## 数据影响

V0.2 的总控优先与默认双格式升级没有修改持久化 Schema，也没有迁移、删除或覆盖既有会话数据。E2E 只创建隔离测试数据。

该结论只适用于本次升级。未来若修改 Schema，必须按 ADR-0001 单独提升 Schema version 并提供迁移方案。

## 后果

正面影响：

- 新版本可以在不覆盖基线的情况下完成真实验收。
- 应用故障的回滚范围限制在目标槽位。
- 数据、密钥、会话和日志边界明确。

成本：

- 需要维护两套服务状态和发布清单。
- 需要额外磁盘保存不可变 release 与回滚点。
- 切换前必须处理活动任务，不能无条件重启。

## 被否决的方案

### 原地覆盖在线目录

被否决，因为无法证明运行文件与测试产物一致，也破坏快速回滚。

### 两槽共享可写数据目录

被否决，因为不同版本可能并发写入不兼容状态，且无法隔离客户数据和审计证据。

### 自动复制客户数据到新槽

被否决，因为数据迁移需要独立授权、兼容性验证和回滚设计，不能作为普通应用发布的隐含动作。

## 不变量

- 不覆盖在线 release。
- 不跨槽共享可写业务状态。
- 不在有活动任务时强制切换。
- 不只回滚应用而保留不匹配的 Skill 绑定。
- 不因目标槽升级而停止或修改另一槽。
- 不在公开文档记录服务器地址、秘密、客户标识或私有运维路径。
