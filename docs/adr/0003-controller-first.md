# ADR-0003：每轮总控优先

- 状态：Accepted
- 日期：2026-08-25

## 背景

早期 V0.2 依赖 Harness 根据 Skill 描述直接选择最匹配专项，并明确允许单一专项任务不经过综合总控。一次真实测试因此只调用了研究专项。该行为并非随机异常，而是旧路由规则的预期结果。

直接专项入口带来三个问题：

- 全局范围、证据和交付判断可能因总控未加载而缺失。
- 专项可能自行调用下游，形成重复或多中心编排。
- 默认文件格式等总控交付规则无法稳定覆盖所有报告类任务。

## 决策

`comprehensive-real-estate-expert` 是工作台每轮唯一入口和唯一编排者。应用构造的 Harness Prompt 第一行固定为：

```text
/comprehensive-real-estate-expert
```

总控激活后再通过 Harness 内置 `skill` tool 调用必要专项。

### 后端硬约束

- 服务端常量定义唯一总控 ID，并把 slash command 放在 Prompt 第一行。
- 当前请求使用 JSON 编码，用户输入不能把另一个 slash command 提升为服务端入口。
- 每一轮使用同样的构造函数，因此首轮、续聊和恢复后的新运行遵守同一规则。
- 总控文件缺失时，Ready 不通过，运行在创建 Harness 执行前 fail closed。

硬约束保证的是“应用提交了确定性的总控入口”和“缺少入口文件时不运行”。总控是否被 Harness 实际加载，还需要 Harness 会话证据或集成测试确认。

### Prompt / Skill 契约

- 总控不得通过 `skill` tool 再次调用自身。
- 单一专项任务执行“总控 → 一个必要专项”。
- 跨模块任务由总控按依赖顺序调用多个专项。
- 总控维护逻辑上的 `loaded_skills`，同一专项每轮最多调用一次，明确失败后才可重试。
- 子 Skill 不直接调用其他 Skill，只返回结果和下一节点需求。

### 软审计

应用记录 `agent.controller.injection.prepared`，用于证明总控入口在运行开始前已经构造。该事件不是一次 runtime `skill` tool 调用，也不能单独证明总控加载成功。

总控正常情况下不出现在子 Skill operation 序列中。有效链应由“总控注入与会话首行证据”加“后续 runtime 专项调用”共同组成。

### E2E 闸门

涉及路由的发布必须验证：

- 持久化 Harness 会话中的实际 Prompt 第一行是总控命令。
- 注入准备事件早于运行开始。
- 专项调用顺序符合用例预期。
- 同一专项没有重复调用，且不存在被忽略的失败。

## 后果

正面影响：

- 单专项和跨模块任务共享一致的范围、证据和交付入口。
- 下游调用责任集中，减少重复和环路。
- 总控级交付策略可以覆盖所有报告类主成果。

成本与风险：

- 每轮都增加一次总控上下文，可能带来少量 token 和路由开销。
- 专项调用顺序及去重当前仍主要依赖 Prompt/Skill 契约，不是后端状态机。
- 总控 Skill 文件存在检查不能证明其内容、版本或 frontmatter 正确。

## 被否决的方案

### 继续完全依赖自动 Skill 描述路由

被否决，因为无法保证单专项任务经过总控，真实测试已经证明该缺口。

### API 用关键词直接选择专项

被否决，因为会把领域路由复制到应用层，导致 Skill 描述、总控规则和 API 三处漂移。

### 总控通过 skill tool 调用自身

被否决，因为会重复加载、增加环路风险，也使审计链难以解释。

## 回滚

本决策同时改变应用 Prompt 构造、System Prompt 和多个 Skill 的交接语义。若必须回滚，应恢复上一组已经共同验证的应用 release、System Prompt 与 Skill 绑定，不得只恢复其中一层。

## 后续工作

如果未来需要把契约升级为更强的运行保证，可增加：

- 总控内容或 manifest 完整性校验；
- 服务端 Skill 调用状态机和去重表；
- 缺失强制交付节点时的终态阻断；
- 覆盖 Product、Social、Wechat 和按需 PDF 分支的独立 E2E。
