# ADR-0004：报告类主成果默认 Markdown + HTML

- 状态：Accepted
- 日期：2026-08-25

## 背景

运行配置早已声明默认格式为 Markdown 和 HTML，但旧版每轮 Prompt 与 System Prompt 没有把它作为报告交付契约。当请求直接命中专项而未加载总控时，真实运行只生成了 Markdown。

配置默认值、模型执行要求和实际文件交付是不同层次。仅在配置中列出两个格式，不能证明一次运行真的生成了两个成果。

## 决策

当本轮主成果属于以下类型，且用户未明确指定最终格式时，默认生成内容对应的 Markdown 与独立 HTML：

- 地产研究；
- 项目分析；
- 策划方案；
- 管理报告。

两个成果应在同一轮生成、非空并可以打开。发布 E2E 进一步要求二者同主名并验证 HTML 基本结构。

默认不生成 PDF。PDF 只有在用户明确要求或任务契约明确需要时才进入生成与逐页技术质检链。

## 例外

以下情况不强制默认双格式：

- 用户明确指定单一格式或其他格式；
- 用户明确不要文件；
- 纯澄清、简短问答或不形成文件成果的局部解释；
- 微信资料转换或归档、社交素材、数据表、模型等已有专项输出契约的任务。

如果专项任务同时形成报告类主成果，主报告仍适用默认双格式。

## 保证分层

### 后端硬约束

- 应用使用固定默认格式常量构造每轮交付策略。
- 输出审计在运行前后比较文件指纹，只统计本轮新增或更新的扩展名。

后端当前不强制生成文件，也不会因为双格式缺失自动把运行标记为失败。

### Prompt / Skill 契约

- System Prompt 把双格式定义为报告类主成果的默认交付契约。
- 每轮 Prompt 明示默认格式、适用范围、例外和“默认不生成 PDF”。
- 总控 Skill 要求实际生成、逐一检查两个非空文件并确认可打开。

### 软审计

运行完成日志记录：

- `run_output_formats`：本轮新增或更新的文件格式；
- `default_output_pair_present_this_run`：本轮扩展名集合是否同时包含 `md` 和 `html`。

这些字段用于检测和回归，不是在线强制闸门。文件指纹基于路径、大小和修改时间，不是内容哈希。

### E2E 闸门

发布验收应检查：

- 新对话在运行前没有可混淆的历史输出；
- 本轮至少生成一个同主名 Markdown/HTML 对；
- 两个文件非空、可下载、可打开；
- 内容包含当前任务的核心主题；
- HTML 包含有效的 `html` 和 `body`；
- 终态软审计同时报告 `md/html` 和 pair=true；
- 未明确要求时没有误调用 PDF Skill。

## 后果

正面影响：

- Markdown 适合审阅、版本控制和内容复用。
- 独立 HTML 适合直接阅读、分享和视觉呈现。
- 用户无需记忆格式参数即可获得两种互补成果。

成本与风险：

- 每次报告任务增加生成、检查和存储成本。
- 当前软审计只验证扩展名集合，不证明内容完全对应。
- 同主名、非空、可打开和 HTML 结构主要由 E2E 验证，而非每次运行的后端强制规则。

## 被否决的方案

### 继续只依赖 runtime 配置默认值

被否决，因为配置值没有稳定进入模型执行上下文，真实运行已出现单格式输出。

### 默认同时生成 PDF

被否决，因为 PDF 需要额外的渲染与逐页技术质检，且技术通过不能替代最终 QA。

### 对所有回答强制生成文件

被否决，因为简短问答和专项转换不需要报告型交付，会造成不必要的运行成本和错误文件。

## 后续工作

若未来需要把双格式升级为后端硬交付闸门，应另行设计：

- 基于本轮声明交付类型的机器可读契约；
- 同主名、非空和可打开检查；
- Markdown/HTML 内容对应度检查；
- 缺失成果时的可恢复失败状态；
- 例外类型的显式、可测试判定。

在这些能力落地前，文档不得声称后端已经强制双格式成功。
