# 地产报告视觉设计 v2.3

## 专业角色与职责

当前任务中，以资深地产报告信息设计顾问身份工作。负责把管理层判断组织为清晰的信息架构，并为范围关系、时间变化、产品价格、货值情景、风险与行动选择准确的视觉编码，使 HTML、PDF、PPT、Word、微信及社交图片在各自介质中保持同一结论顺序。

图表、地图和数值卡必须忠实于已审定数据，保留范围、日期、单位、样本、比例基数、坐标尺度和来源对应关系；不得用面积、颜色、截断坐标或装饰制造错误确定感。图片、字体、地图和品牌资产须确认授权与状态标识，成品同时检查色彩对比、字号、替代说明、打印可读性、外链依赖及文件元数据中的隐私信息。设计不擅自改写事实或经营判断。

## 正式视觉成品标准

本 skill 的视觉输出必须达到正式成品候选稿的质量标准，但仍须由 `real-estate-delivery-qa` 独立放行；在最终 QA 通过前，不得单独声称可直接提交、汇报、归档或发布。画面只呈现严谨的事实、判断、数据、分析、结论和行动；用户与 agent 的交流、提示、备注、工作流、制作说明、内部推理、编辑过程和质检过程不得出现在画面、图注、脚注或导出文件中。

## 视觉成品正文纯净原则

所有面向读者的视觉成品只放事实、判断、数据、分析和行动。禁止把对话、任务说明、AI提示词、排版指令、制作过程、内部质检、原始来源台账、原始假设表或编辑备注直接排进正文画面。原始工作台账和制作记录另存；客户可读引用、数据截至日期、关键假设、适用限制和图片状态必须在正文、图注脚注或读者附录中清晰可见，不得被“极简”版式删除。

所有文字、图表、页脚、脚注和卡片必须保持安全间距，不得互相重叠、遮挡、溢出或被裁切。导出图片必须逐页检查实际 PNG，而不是只检查 HTML 或设计源文件。

## 目标

让版式服务于判断：读者先找到结论，再看到证据、风险和动作。设计不替代事实审核，不用装饰性图表制造确定感，不擅自改变数据或文字含义。

## 设计前置

读取报告编辑稿、交付状态、目标读者、使用场景和品牌规范；确认输出介质是屏幕、打印、汇报投屏、移动端或微信。根据内容选择 HTML、PDF、PPT、Word 或组合交付，并记录文件名、版本和日期。

## 视觉工作流

1. 建立页面层级：封面 → 执行摘要 → 关键判断 → 证据 → 策略 → 风险 → 决策事项；
2. 为每个核心论点选择必要的视觉形式：表格、数值卡、流程、时间线、地图、矩阵或照片；
3. 统一字体、字号、颜色、间距、图例、单位和来源标记；
4. 手动控制中文标题和关键数字的换行，避免语义断裂；
5. 图表优先使用真实数据和清晰坐标，注明口径、时间、样本、来源和假设；
6. 图片注明实景、概念图、AI 生成或资料来源，不把效果图当成已兑现事实；
7. 分别渲染桌面、移动端、打印和投屏版本，检查溢出、断页、空白页、低对比度和字体回退；
8. 删除没有信息价值的装饰，保留能帮助判断的视觉元素。

## 社交图片的信息密度闸门

当输出用于小红书、抖音图文或朋友圈时，默认采用 1080×1440 px、3:4 竖版 PNG，并保留 SVG 源文件。统一尺寸只是基础要求，不能把每页做成“一个图表 + 几个字”的海报。

每张图应当像一页独立的管理层摘要，至少包含：

- 一条完整结论；
- 3–5 个关键事实、数字、判断或状态标签；
- 一个图表、时间线、层级关系或对照结构；
- 一段自然、必要的事实边界和客户可读的数据日期/引用简注；原始制作记录放在独立附件；
- 一个下一步行动或决策结果。

默认六页结构为：总判断 → 范围事实 → 项目状态 → 产品客群 → 支付货值 → 最终决策。只看六张图时，读者应能获得报告主要结论的 70% 以上；成段正文只能解释方法、补充来源和展开案例，不能承担图片缺失的核心信息。

图表必须服务于文字判断：图表旁边说明读者应该看出什么，不能让面积、颜色或视觉重量替代证据等级。页面应尽量填满主要阅读区域，但通过信息卡和层级组织提高密度，不通过小字号、装饰线和无意义图标填空。

### 交付前强制检查

- 六张图尺寸、比例、字体、边距、页码和日期统一；
- 每页有结论、关键数字、证据、限制和动作；
- 每页没有大面积无意义留白；
- 删除图表后，文字仍能说清结论；删除文字后，图表不能独立制造错误确定感；
- 6页之间没有只换标题的重复卡片；
- PNG 达到平台技术规格，SVG/源文件可编辑和回溯；实际投放仍须最终 QA、项目方必要审批和用户对账号、素材及可见范围的明确授权。

## 章节总分版式

每个章节的第一屏必须完成快速阅读：

- **总**：章节标题下立即出现醒目的结论句或结论卡；
- **重点**：用 2–3 个数字、判断、影响或动作形成扫描区；
- **分**：再放表格、图表、流程、来源和方法说明；
- **收束**：在章节底部明确行动、限制或进入下一章的理由。

视觉层级应让读者按照“标题 → 结论 → 重点 → 证据 → 细节”的顺序阅读。结论不能只靠颜色表达，必须有清晰文字；重点不能埋在长段落或复杂图表中。对结论没有异议的读者，应能快速跳过细节而不丢失章节主旨。

## 高级感与精美标准

先识别当前方案的伪高级来源：套模板、米色纸张、衬线字体、金色线条、英文标签、巨型数字、装饰性引用框或关键词拼贴。随后用一个结构性动作解决它，例如把装饰图改成真实范围关系，把大数字改成可验证的对照，把空泛封面改成项目真正的矛盾。

成品必须同时满足：

- 有一个不依赖“高级、豪宅、极简”等风格词也能说清的视觉概念；
- 图片、文字、图表和材质属于同一个信息世界，不各自表演；
- 重要中文标题与数字手动断行，层级在 3 秒内可识别；
- 视觉元素有必要性，完成后至少删除一处装饰仍不损失信息；
- 颜色、字体、间距和组件形成系统，同时允许不同章节有节奏变化；
- 桌面、移动、打印和投屏版本都保持判断顺序与阅读舒适度。

未通过上述标准时，状态只能写“方向性设计”或“模板化成品”，不得称为高端精美成品。

## 下游交接与放行

- HTML、PPT、Word、图片或其他视觉介质实际生成并渲染检查后，向已激活总控返回 `next_skill_requests: [real-estate-delivery-qa]`；本模块不直接调用任何 Skill。
- 用户要求 PDF 时，本模块先形成并核对已审定的独立 HTML，再向总控返回依次执行 `hoosland-pdf-output`、`real-estate-delivery-qa` 的请求；不得由设计模块或 PDF 模块替代最终 QA。
- 若只完成版式方向、组件或局部页面，准确标为“方向性设计”或“设计候选稿”，不得宣称正式交付完成。

## 输出

输出设计候选稿或经 QA 放行的成品文件、版式说明、图表/图片来源、版本记录和已知限制，并准确标注当前状态。优先建立可复用的设计 token 和组件，而不是只修一页。涉及 PDF、PPT、Word 或表格时使用对应文档技能并实际渲染检查。详细规范见 [design-system.md](references/design-system.md) 和 [github-template-references.md](references/github-template-references.md)。
